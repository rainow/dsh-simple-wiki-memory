# reference/skills/ — 技能记忆

这里存 **调用 skill / MCP 时要用**的稳定外部事实与坑点（ID、枚举值、端点、配额、"必须先做 X"这类）。
**插件的改造 / 补丁 / 升级类不在这里** —— 那类归 `reference/` 顶层（如 `reference/ds-harness-remote.md`）。
完整规则见 `~/.dsh/AGENTS.md`：规则 2（第 0 步判据 + 准入四道闸 + 记录规范 + 晋升 lint）· 规则 6（检索）· 规则 7（出错即回报）。

## 归属怎么判（看「读它的那一刻」）

1. **调用某个工具时要用**的事实（参数、`code` / `id`、端点、配额、一步都不能错的顺序）→ 放这里
2. **改造 / 升级 / 排障 / 讨论**某个东西时读的内容（补丁、构建、配置项、PR 步骤）→ 放 `reference/`；**DSH 插件在顶层**，不进这里
3. 专有标识符只是线索：满篇 `code` / `id`，但记它们是为了「改它」→ 仍归 `reference/`
4. 两类都有 → 按「下次什么时候会打开它」定主体；跨工具的偏好另存 `reference/`，**并在这里加一行指针**
5. 犹豫超过一秒 → 问用户，不要猜
6. 拟定的文件名里含工具名（`mcd`、`blender`）→ **先回答第 1 问**，别因为名字像工具就默认放这里

## 命名

- skill：`<skill-id>.md`（小写；`/` → `__`）
- MCP：`mcp-<server-name>.md`
- 以 `_` 开头的文件是说明文档，不是技能记忆

## 模板

```markdown

skill: <skill-id>          # 或 mcp: <server-name>

---

| 用途 | 值 |
|---|---|

## 必传参数 / 特调

## 坑

- 现象 → 结论
```

## 硬规矩

1. **不写流程** —— 流程属于 SKILL.md，会随 skill 更新
2. **不写密钥** —— 密码 / token / API key / 私钥、与用途无关的个人安全细节
3. **冲突不覆盖** —— 新旧矛盾时标 ⚠️、两条都留，让用户判断
4. **删除测试** —— 每行问「删掉它，下次会出错吗？」不会就删
5. **三类禁写** —— 工具 schema 已声明的 / 能现场查到的（价格、地址全称、余额）/ 会变的
6. **预算** —— 单文件 ≤ 6KB / 80 行；超了先压缩，压不下去再向用户申请超限
7. **不写变更记录** —— 用 frontmatter `verified_at`；只留结构性变更一行
8. **与 SKILL.md 去重** —— SKILL.md 已有的不重复存；发现重复以 SKILL.md 为准删除

## 出错怎么办

用起来发现记忆与实际不符 → **先标 `❓待核实（日期）`，不要静默改数** → 写 pending 说明
「原记录 / 实际 / 证据」→ 当场告诉用户 → 确认后再改并更新 `verified_at`。
